# DEPLOYMENT.md — вывод системы в интернет с ограниченным доступом

Этот документ — пошаговая инструкция для **вас** (часть, требующая доступа к роутеру, DNS-панели регистратора домена и физической машине, на которой крутится Docker Desktop — этого у меня нет). Код и конфигурация уже подготовлены: docker-compose.yml биндит порты db/backend/frontend только на `127.0.0.1` (раньше слушали на всех интерфейсах), добавлен Caddy как единственная точка входа на портах 80/443 с автоматическим HTTPS (Let's Encrypt), фронтенд везде использует относительный путь `/api` (раньше — захардкоженный `http://localhost:8000/api`, что не работает с реального домена), добавлен `backup_finance.bat` для регулярных бэкапов.

Модель доступа: систему защищает её собственный логин/пароль (JWT + RBAC, уже реализован) — то есть это **не** VPN и не IP-белый список, а обычный сайт за доменом с HTTPS, куда могут зайти все, у кого есть учётка в системе. Если впоследствии понадобится более строгая изоляция (например, ограничить доступ только сотрудникам с конкретных IP), это отдельная задача — см. раздел «Возможные дальнейшие шаги» в конце.

## Шаг 1 — Домен

Нужен домен (свой или поддомен, например `finance.ваша-компания.ru`). Если домена ещё нет — купить у любого регистратора (Reg.ru, Namecheap, Cloudflare Registrar и т.п.).

## Шаг 2 — Узнать внешний IP этой машины и настроить DNS

1. Узнайте текущий публичный IP машины — откройте в браузере на этой машине `https://2ip.ru` или `https://whatismyip.com`.
2. В DNS-панели регистратора домена создайте A-запись: `finance.ваша-компания.ru → <этот IP>` (или просто домен второго уровня, если используете его целиком).

**Важный нюанс для домашнего/офисного интернета:** если провайдер не выдаёт статический IP (он у вас может периодически меняться), DNS-запись «отвалится» при следующей смене IP. Проверить: посмотрите IP сегодня и через пару дней — если совпадает, скорее всего статический (или с очень долгой арендой) и можно использовать обычную A-запись. Если меняется — нужен Dynamic DNS (например, бесплатный DuckDNS или No-IP, либо Cloudflare с скриптом-обновлятором) вместо обычной A-записи. Это можно решить отдельно, не блокирует остальные шаги.

## Шаг 3 — Проброс портов на роутере

В админке роутера (обычно `192.168.0.1` или `192.168.1.1`) настройте перенаправление портов (port forwarding / virtual server):

- Внешний порт `80` → внутренний IP этой машины : порт `80`
- Внешний порт `443` → внутренний IP этой машины : порт `443`

Внутренний IP машины — `ipconfig` в cmd, поле "IPv4 Address" сетевого адаптера. Если он выдаётся по DHCP и может меняться — в роутере имеет смысл закрепить его за MAC-адресом машины (DHCP reservation / static lease), иначе проброс портов рано или поздно перестанет указывать туда, куда нужно.

## Шаг 4 — Открыть порты в Windows Firewall (если стоит сторонний антивирус с собственным файрволом — аналогично там)

Docker Desktop обычно сам открывает нужные порты для контейнеров, но если входящие подключения извне всё равно не доходят — добавьте правило Windows Defender Firewall: разрешить входящие TCP 80 и 443.

## Шаг 5 — Указать домен в `.env` и перезапустить

В файле `.env` (в корне проекта, рядом с `docker-compose.yml`) замените:

```
DOMAIN=localhost
```

на

```
DOMAIN=finance.ваша-компания.ru
```

Затем из `cmd` (не PowerShell — см. CLAUDE.md про кириллицу) в корне проекта:

```
docker compose up -d
```

Caddy подхватит новое значение `DOMAIN` при пересоздании контейнера, обратится к Let's Encrypt по HTTP-01 challenge (он требует, чтобы порт 80 снаружи реально указывал на эту машину — то есть шаги 2–4 должны быть выполнены и DNS должен успеть обновиться, обычно от нескольких минут до часа) и автоматически получит сертификат. Логи можно посмотреть через `docker logs finance_caddy` — если домен/DNS/проброс настроены верно, там будет видно успешное получение сертификата; если что-то не так, Caddy будет повторять попытки и писать в лог причину (чаще всего — DNS ещё не обновился или порт 80 не доходит снаружи).

## Шаг 6 — Проверка

1. Откройте `https://finance.ваша-компания.ru` с **другого** устройства не в этой локальной сети (например, с телефона через мобильный интернет, не через Wi-Fi роутера) — это подтверждает, что доступ действительно идёт снаружи, а не просто резолвится локально.
2. Залогиньтесь под существующей учёткой — должно работать как обычно.
3. Убедитесь, что браузер показывает действительный сертификат (замочек без предупреждений) — если сертификат самоподписанный/невалидный, значит Let's Encrypt не выдал сертификат и нужно смотреть `docker logs finance_caddy`.

## Постоянная работа машины

Эта схема работает только когда сама машина включена, Docker Desktop запущен и есть интернет — это обычный домашний/офисный сервер, а не облако. Если машина выключится или Docker Desktop не поднимется автоматически после перезагрузки Windows — система станет недоступна снаружи. Если нужна гарантированная доступность 24/7, рассмотрите: автозапуск Docker Desktop при старте Windows (Settings → General → "Start Docker Desktop when you sign in"), отключение сна/гибернации на этой машине, ИБП на случай отключения электричества.

## Резервные копии

`backup_finance.bat` уже готов (делает `pg_dump`, проверяет, что дамп не пустой, хранит последние 14 копий, пишет лог в `backups\backup_log.txt`). Зарегистрируйте его в Windows Task Scheduler:

1. Task Scheduler → Create Basic Task.
2. Триггер: Daily, время, когда система не используется (например, 03:00).
3. Action: Start a program → путь к `backup_finance.bat` в корне проекта.
4. В свойствах задачи отметьте "Run whether user is logged on or not", чтобы бэкап шёл даже если никто не залогинен в Windows.

Бэкапы лежат в `backups\` **локально на этой же машине** — это защищает от порчи данных (плохой импорт, ошибочное удаление), но не от отказа диска/машины целиком. Имеет смысл периодически копировать `backups\` на внешний носитель или в облако (Dropbox, в котором уже лежит сама папка проекта, эту папку синхронизирует автоматически, если её не исключили из синхронизации).

## Секреты

`.env` (там `POSTGRES_PASSWORD` и `SECRET_KEY`) **никогда** не должен попасть в git — он уже в `.gitignore`, проверьте, что это осталось так после любых будущих правок `.gitignore`. Если когда-либо `.env` случайно засветится (коммит, скриншот, отправка архива целиком) — сразу сгенерировать новые значения и заменить (смена `SECRET_KEY` разлогинит всех; смена пароля Postgres требует `ALTER USER` внутри контейнера, простая правка `.env` недостаточна для уже существующей базы — см. `AUDIT.md`/`IMPLEMENTATION_PLAN.md`, Этап 3).

## Возможные дальнейшие шаги (не обязательны для запуска, но стоит знать)

- **IP-ограничение в дополнение к логину/паролю** — если впоследствии понадобится пускать только из определённых сетей (офис, известные адреса сотрудников), это настраивается в `Caddyfile` (директива `remote_ip`) без изменений в backend.
- **2FA** — система сейчас защищена только паролем; если нужна двухфакторная аутентификация, это отдельная доработка `auth.py` + фронтенда логина.
- **Мониторинг аптайма** — простой внешний пинг (UptimeRobot и аналоги, бесплатный план) подскажет, если машина/контейнеры упали, не дожидаясь жалобы пользователя.
