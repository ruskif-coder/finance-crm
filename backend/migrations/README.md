# backend/migrations — изменения схемы и данных

Одна папка, один формат, хронологический порядок. Alembic в проекте не используется
(зависимость убрана 2026-08-22) — миграции пишутся сырым SQL и накатываются руками.

## Имя файла

```
<ГГГГ-ММ-ДД>_<что>.sql
```

Дата впереди, поэтому `ls` — это история изменений схемы по порядку. Вид работы, если он
не схема, входит в имя: `2026-08-16_seed_backlog.sql`. До 2026-08-23 сиды назывались
`seed_backlog_<дата>.sql` и выпадали из общего порядка — переименованы.

## Шапка файла

Первая строка — комментарий с назначением. Пишем **зачем**, а не **что**: «что» и так
видно из SQL. Русские значения перечислений сравниваются в коде буквально — писать точно.

```sql
-- Строка финансового отчёта у статьи. Группа справочника отвечает за вид реестра,
-- а разметка — за отчёт: одна группа собирает статьи с разной судьбой.
ALTER TABLE articles ADD COLUMN IF NOT EXISTS pl_line VARCHAR;
```

## Обязательное правило: повторный накат

Каждый файл должен переживать повторный запуск: `CREATE TABLE IF NOT EXISTS`,
`CREATE INDEX IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `INSERT … ON CONFLICT DO NOTHING`.
Таблицы учёта применённого в проекте нет (см. ниже), поэтому единственная защита от
двойного наката — идемпотентность самого файла.

На 31.08.2026 файлов 69, и правило проверено ПРОГОНОМ, а не чтением: все 37 миграций
релиза накатаны на чистую базу в порядке ниже, затем накатаны ещё раз. Второй проход нашёл
два файла, которые повторно не проходили (`CREATE OR REPLACE VIEW` не умеет убирать
колонки, а поздние миграции эти представления расширили) — оба переписаны на
`DROP VIEW IF EXISTS` + `CREATE VIEW`. Третий и четвёртый проходы чистые.

**Ничего не удалять.** Устаревшее поле замораживается: колонка остаётся, код перестаёт её
читать. Так сделано с `Counterparty.contract_number/contract_date` и `Contract.payment_term`.

## Как накатить и как проверить

```bash
docker exec -i finance_db psql -U finance_user -d finance < backend/migrations/<файл>.sql
```

Перед любой правкой боевых данных — бэкап:

```bash
docker exec -t finance_db pg_dump -U finance_user finance > backups/before_<что>_<дата>.sql
```

Проверять фактом, а не отсутствием ошибки: `\d <таблица>` в psql.

Порядок выкладки: миграция накатывается **до** кода. На проде — только с явного
разрешения владельца (навык `deploying-to-prod`).

## Что сюда НЕ кладём: попавшее в гит остаётся навсегда

Файл, попавший в `backend/migrations/`, живёт в истории репозитория вечно — удаление из
рабочего дерева его оттуда не убирает.

До 31.08.2026 здесь стояло обоснование «GitHub-репозиторий открыт». Оно неверно: проверено
23.08.2026, репозиторий приватный. Правило от этого не слабеет, а становится точнее —
приватность это НАСТРОЙКА, её однажды переключат одним щелчком, и реквизиты из истории
после этого уже не достать.

Сюда идут только миграции **без опознавательных данных**: DDL, ограничения, индексы,
безличные сиды (права, стадии, форматы).

Разовые правки данных, где в комментариях или в `WHERE` стоят реальные контрагенты, суммы,
ИНН, счета или адреса, живут в корневой папке `scripts/` — она в `.gitignore` целиком и
именно за этим. Там же лежат `.bat`-помощники, пентест-набор и скрипты с реальными
реквизитами. Соглашение об имени файла там то же самое (дата впереди), чтобы порядок
читался одинаково в обеих папках.

Проверка перед переносом файла сюда — одной командой:

```bash
grep -niE "инн|бик|счёт|[0-9]{18,}|ООО|@" backend/migrations/<файл>.sql
```

Живой пример, почему это правило записано: `2026-08-10_fix_invoice_dates.sql` исправлял
18 переставленных дат счетов, и в комментариях к каждой строке стояло название
контрагента — то есть кусок списка клиентов. Файл остался в `scripts/`.

## Где ещё живёт схема (важно знать)

Схему определяют **три** механизма, и это не опечатка:

| механизм | что делает |
|---|---|
| `Base.metadata.create_all()` | создаёт таблицы и колонки из ORM-моделей на пустой базе |
| стартовый блок `app/main.py` (стр. ~36–130) | `ALTER TABLE … ADD COLUMN IF NOT EXISTS` для баз, которые уже существовали |
| эта папка | всё, чего не умеют первые два: правки данных, ограничения, сиды, перечисления |

**Таблицы учёта применённых миграций нет.** Ответить на вопрос «эта миграция накачена на
проде?» можно только посмотрев в саму базу.

## Замер 2026-08-23 (чтобы не выводить заново)

- Схемы локального стенда и прода **совпадают полностью**: 686 колонок, расхождений ноль.
  Единственная разница — две таблицы Диадока (`diadoc_documents`, `operation_documents`),
  которых на проде нет, потому что модуль ещё не в гите.
- Стартовый блок `main.py` заводит **44 колонки — все 44 уже объявлены в ORM-моделях.**
  Значит на пустой базе их создаст `create_all`, а на существующих они давно есть. Блок
  сегодня выполняется вхолостую при каждом старте контейнера.
- Из 6 индексов блока **4 объявлены только в нём** и отсутствуют в ORM:
  `ix_sales_deals_year_plan_line`, `ix_sales_deals_plan_link`, `ix_sales_year_plan_lines_plan`,
  `ix_notifications_user_unread`. Убрать блок, не перенеся их в модели, — потерять индексы
  на новой базе.
- Три разрушающие операции блока — **пустышки** на обоих стендах (цель давно удалена):
  `DROP TABLE IF EXISTS sales_service_variants`,
  `ALTER TABLE sales_services DROP COLUMN IF EXISTS platform` и то же для `currency`.
  Опасность не в сегодня, а в завтра: если кто-то заведёт колонку `platform`, она молча
  исчезнет при следующем рестарте.
- Правка данных `UPDATE sales_deals SET plan_deal_idx = 0 …` — тоже пустышка (0 строк).
- 7 колонок и 4 индекса объявлены **дважды**: и в блоке, и в миграции
  (`2026-08-12_deal_code`, `2026-08-12_year_plan_packages`, `2026-08-13_plan_deal_idx`).

## Нужны ли миграции после применения? Проверено экспериментом

Вопрос правильный, и ответ не «конечно да». Проверка: на пустой базе выполнен один
`create_all()` из ORM-моделей, результат сравнён с боевой.

**Получилось 76 таблиц из 78 и 694 колонки из 714.** То есть подавляющее большинство файлов
здесь после применения — **история, а не машинка**: всё, что они создают, уже описано в
моделях, и на новой базе появится само.

Но недостача оказалась не там, где ожидалось:

| чего не хватает | где рецепт |
|---|---|
| таблица `bank_balances` | **нигде в контроле версий** — только в дампах `backups/` |
| таблица `company_settings` | `scripts/2026-07-08_migrate_alfa_export.sql`, то есть вне гита |
| 5 колонок `contracts`: `doc_type`, `edo_signed_at`, `edo_status`, `nds`, `own_legal_role` | **нигде** — заведены мимо кода, в ORM их нет, и ни одна строка кода их не читает |
| 66 индексов (210 против 144) | миграции и стартовый блок `main.py` |

Отсюда три вывода:

1. **Поднять рабочую базу из репозитория сегодня нельзя.** Не хватит двух таблиц, и
   приложение упадёт на экране остатков: `settings.py` и `reports.py` читают
   `bank_balances` сырым SQL.
2. **Удалять миграции нельзя**, но не ради схемы, а ради **индексов**: две трети из них
   заводятся здесь и в стартовом блоке, а не моделями.
3. Пять колонок `contracts` — мусор в самой базе: заведены разово, никем не читаются.
   По правилу проекта их не удаляют, а замораживают; но записать, что они есть и что они
   не используются, стоит — иначе следующий человек будет гадать.

### Недостача закрыта 2026-08-23

Написаны две миграции, снятые с боевой базы один в один:

* `2026-08-23_bank_balances_company_settings.sql` — две таблицы, которых не было в
  контроле версий никогда;
* `2026-08-23_missing_indexes.sql` — 25 индексов и 2 ограничения уникальности,
  заводившиеся разово. Среди ограничений — `role_permissions (role_id, section)`:
  без него роль может получить две строки прав на один раздел, и какая подействует —
  вопрос везения.

**Проверено экспериментом, а не намерением.** На чистой базе выполнен полный старт
приложения, накатаны все миграции, затем эти две. Результат против боевой:

| | боевая | чистая после наката |
|---|---|---|
| таблиц | 78 | **78** |
| индексов | 210 | 217 |
| колонок | 714 | 709 |

Разница объяснена целиком:

* **+7 индексов у чистой** — это не недостача прода, а избыточные объявления в ORM:
  `ix_*_id` поверх первичного ключа (у него индекс и так есть) и дубли того, что
  стартовый блок `main.py` уже создаёт под другим именем
  (`ix_sales_deals_year_plan_line` против `ix_sales_deals_year_plan_line_id`).
  Кандидаты на снос отдельным решением.
* **−5 колонок у чистой** — `contracts.doc_type`, `edo_signed_at`, `edo_status`, `nds`,
  `own_legal_role`. Заведены мимо кода (похоже, при работе с ЭДО), в ORM их нет, и **ни
  одна строка кода их не читает**. Воспроизводить мёртвые колонки на новой базе не нужно,
  поэтому в миграции они не вошли. Удалять их с боевой тоже не нужно — по правилу проекта
  устаревшее замораживается; эта запись и есть заморозка.

Обе новые миграции проверены на живой базе: 714 колонок / 210 индексов / 340 ограничений
до и после, ни одного изменения — только «already exists, skipping».

**Итог по исходному вопросу.** Старые миграции как «то, что надо накатывать» почти не
нужны — их схему давно держат ORM-модели. Но удалять их нельзя: две трети индексов
заводятся именно там. Теперь репозиторий впервые может поднять работающую базу с нуля,
и вопрос «нужны ли старые миграции» стал вопросом об архиве, а не о работоспособности.

## Предложение по порядку (требует решения владельца)

1. Перенести 4 «бесхозных» индекса в ORM-модели — тогда стартовый блок станет полностью
   избыточным, а `create_all` перестанет терять их на новой базе.
2. Убрать из блока три пустых разрушающих операции — они уже отработали.
3. Завести таблицу учёта применённого и внести в неё существующие миграции как
   применённые. **Это изменение схемы — согласуется до реализации** (навык
   `changing-db-schema`).
4. После этого блок из `main.py` выносится в скрипт, запускаемый явно при деплое, а в
   `main.py` остаётся только `create_all`.

Пункт 4 без пунктов 1–3 делать нельзя: сегодня схему на существующих базах синхронизирует
именно блок, и его удаление в одиночку оставит новые окружения без индексов, а старые —
без механизма догона.

### Почему не по алфавиту

Имена файлов дают хронологию, но внутри дня 28 августа алфавит ломает зависимости
**трижды**:

| Алфавит ставит раньше | А зависит от | Что произойдёт |
|---|---|---|
| `2026-08-28_cabinet_dashboard` | `_publisher_cabinet` | нет схемы `pub` → падение |
| `2026-08-28_cabinet_org` | `_publisher_cabinet` | нет `cabinet_account`, нет `allowed_publisher_ids()` → падение |
| `2026-08-28_pair_file_kind` | `_traffic_queue` | нет таблицы `launch_prep_pair_file` → падение |

Простой `for f in *.sql; do psql < "$f"; done` упадёт три раза и оставит базу в
промежуточном состоянии. **Таблицы учёта применённых миграций в проекте нет** —
единственная страховка в том, что все файлы повторно накатываемы (коммит `b278f59`), то
есть после починки порядка прогон можно повторить целиком.

### Как накатывать

По одному файлу, читая вывод. Не «прошло без ошибки», а **что именно напечатало**:

```
docker exec -i finance_db psql -U finance_user -d finance < backend/migrations/<файл>
```

Три файла печатают сводку, которую надо прочитать глазами:

- **№22** — какие роли получили `creatives` и `dir_publishers_cabinets`. Пустая строка или
  `WARNING` означает, что роли с ожидаемыми названиями на этой базе не нашлись, и права не
  достались никому. Роли ищутся по `label`; сверить заранее:
  `SELECT id, key, label FROM roles ORDER BY id;`
- **№33** — сколько представлений `pub` получили барьер. Должно быть «13 из 13».
- **№34** — права роли `cabinet` на схему `public`. Должно быть `USAGE = f, CREATE = f`.

### Что миграции НЕ делают — руками после

1. **Право входа и пароль роли базы.** Миграция №17 создаёт роль `cabinet` намеренно
   `NOLOGIN` и без пароля: файл лежит в гите. Пароль берётся из `.env`:

   ```
   ALTER ROLE cabinet WITH LOGIN PASSWORD '<CABINET_DB_PASSWORD>';
   ```

   Без этого схема `pub` полностью на месте, всё выглядит накатанным, а кабинет отдаёт 500.

2. **Подписки на уведомления.** Миграция №28 создаёт профили `traffic` и `publishers`, но
   подписки считаются от реестра событий скриптом. На старте ядро вызывает только
   раскладку людей по профилям:

   ```
   docker exec finance_backend python -m app.notify.seed_profiles
   ```

3. **Проверка факта.** После наката — `\d <таблица>` по нескольким новым, а не доверие
   отсутствию ошибок. Быстрая сводка:

   ```sql
   SELECT count(*) FILTER (WHERE table_schema='pub') AS view_pub,
          count(*) FILTER (WHERE table_name LIKE 'launch_prep%') AS launch_prep,
          count(*) FILTER (WHERE table_name LIKE 'cabinet%') AS cabinet,
          count(*) FILTER (WHERE table_name LIKE 'ord_%') AS ord
     FROM information_schema.tables;
   ```

   На стенде после полного наката: 13 представлений `pub`, 106 таблиц `public`.

### Порядок относительно кода

**Миграции идут ДО выкладки кода.** Обратный порядок означает, что первый же запрос уйдёт
в отсутствующую таблицу. Плюс отдельная тонкость: `Base.metadata.create_all()` на старте
ядра заведёт из ORM-моделей бо́льшую часть новых таблиц самостоятельно, и тогда
`CREATE TABLE IF NOT EXISTS` в миграции станет пустышкой. Для `launch_prep_*` это
безопасно (модели повторяют все ограничения), но трёх таблиц в моделях нет вовсе —
`cabinet_account_mute`, `publisher_request`, `publisher_recon`, — и до наката соответствующие
экраны будут отдавать 500.
