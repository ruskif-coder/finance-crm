# Накат миграций на прод

Схема меняется сырым SQL. Порядок наката задаёт список в
[`backend/migrations/README.md`](../../backend/migrations/README.md), раздел «Порядок»;
что уже применено — таблица `schema_migrations`, своя в каждой базе (с 11.09.2026).

## Правила, которые нарушать нельзя

1. **Только через `deploy.sh migrate`.** Он и бэкапит перед накатом, и выбирает базу по
   пути файла, и записывает факт в `schema_migrations`. Прямой `psql < файл` сработает и
   **ничего не запишет** — учёт промолчит ровно в том случае, про который потом важнее
   всего вспомнить: что-то накатывали руками в спешке.
2. **Бэкап до наката.** Делается сам, и при неудаче миграция НЕ накатывается.
3. **По одному файлу, читая вывод.** Не «прошло без ошибки», а что именно напечатало:
   часть миграций печатает сводку бэкфилла, и ноль в ней бывает как нормой, так и
   признаком, что зацепило не те строки.
4. **Никогда `for f in *.sql`.** Алфавитный порядок уже трижды ломал зависимости:
   у файлов от одной даты порядок задаёт не имя, а смысл.
5. **Миграция сначала, код потом.** Иначе первый же запрос упадёт на отсутствующей
   таблице.
6. **`dsp/` — в ДРУГУЮ базу.** Перепутать — значит завести hypertable рядом с боевыми
   деньгами. С 11.09.2026 базу выбирает сам скрипт по пути файла, но при ручном накате
   это по-прежнему на вас.

## Перед выкладкой: проверить, что миграции доедут

Гейт `tests/test_migrations_inventory.py` следит, чтобы каждая свежая миграция была
названа в списке README. Но он не видит гита, поэтому **на хосте**, до пуша:

```bash
git status --porcelain --ignored backend/migrations | grep '^!!' && \
  echo "ВНИМАНИЕ: эти миграции игнорируются и на прод не приедут"
```

Пусто — хорошо. Это ровно тот инцидент, что случился 06.09.2026: каталог `dsp/` целиком
съедался правилом `.gitignore`, и на проде миграций просто не появилось.

## Порядок действий

```bash
ssh root@<сервер>
cd /root/finance

# 0. что уже накачено, а что нет
bash deploy.sh migrate-status

# 1. забрать код (см. ниже про разошедшиеся конфиги)
bash deploy.sh pull

# 2. по одному файлу, в порядке из README
bash deploy.sh migrate backend/migrations/<файл>.sql

# 3. файлы из dsp/ — той же командой: базу скрипт выберет сам по пути
bash deploy.sh migrate backend/migrations/dsp/<файл>.sql

# 4. проверить СОСТАВ, а не код возврата
docker exec finance_db psql -U finance_user -d finance -c "\d <таблица>"

# 5. только теперь код
bash deploy.sh backend
bash deploy.sh frontend
```

## Разошедшиеся конфиги: порядок сохранения

На проде `docker-compose.yml` и `Caddyfile` **всегда** локально изменены. Слепой
`git checkout --` сотрёт сервис бэкапов и связность с соседним продуктом.

```bash
cp docker-compose.yml /root/compose.prod.$(date +%F).bak
cp Caddyfile /root/caddy.prod.$(date +%F).bak
git checkout -- docker-compose.yml Caddyfile
git pull --ff-only origin main
# вернуть прод-версии, СВЕРИВ, не появилось ли в репозиторной версии нужных изменений
cp /root/compose.prod.$(date +%F).bak docker-compose.yml
cp /root/caddy.prod.$(date +%F).bak Caddyfile
chmod +x deploy.sh          # в гите 644, на проде нужен 755
```

Сверять обязательно: новые переменные окружения и новые тома приезжают именно в
`docker-compose.yml`, и молча потерять их — значит получить контур, где функция есть,
а переменной до процесса не доходит.

## Что показывает `migrate-status`

| строка | что значит |
|---|---|
| `накачено` | файл есть в учёте, сумма совпала |
| `НЕ ПРОВЕРЕНО (из бэкфилла)` | строка из бэкфилла 11.09.2026. Означает «скорее всего накачено», а НЕ «накачено»: список писался по каталогу файлов, а не по состоянию базы. Репетиция на копии прода нашла две такие миграции, которых на проде не было. Сомневаетесь — проверьте `\d` руками |
| `НЕ НАКАЧЕНО` | файл в каталоге есть, записи нет. Либо ещё не накатывали, либо накатили мимо скрипта |
| `ИЗМЕНЁН ПОСЛЕ` | имя совпало, сумма — нет: файл правили уже после наката. В базе НЕ то, что лежит в файле |
| `ФАЙЛА НЕТ` | запись есть, файла нет: переименовали или удалили |
| `БАЗА НЕДОСТУПНА` | до базы не достучались. Это **не** «ничего не накачено» — по такому выводу накатывать нельзя |

Вывод разбит на две части — по одной на каждую базу (`finance` и `dsp_analytics`). Если
второй части нет вовсе, значит обход оборвался: до 11.09.2026 он обрывался всегда, и
раздел `dsp_analytics` не печатался ни разу.

## После наката

- открыть **Настройки → Состояние системы** и убедиться, что ни одна проверка не покраснела;
- завести записи в **бэклог отладки** на то, что может выстрелить. Главное поле — как
  поломка выглядит **со стороны пользователя**, плюс срок наблюдения;
- настройки живут в базе и с деплоем **не переезжают**: если функция читает значение из
  настроек, его надо проставить на проде руками.

## Если пошло не так

Отката одной командой нет. Путь назад — восстановление из дампа, снятого перед накатом:
см. [бэкап и восстановление](backup-and-restore.md). Поэтому пункт 2 и не обсуждается.
