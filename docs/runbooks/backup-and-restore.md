# Бэкап и восстановление

> **Дамп, который никто не разворачивал, — не бэкап, а файл.** Это не фигура речи: у
> дампа бывает не тот формат, у ролей — не те права, у расширений базы — не та версия, и
> узнаётся это ровно в тот момент, когда восстановление нужно по-настоящему.

## Что бэкапится

| | чем | куда |
|---|---|---|
| основная база `finance` | `deploy.sh backup` вручную; сервис `finance_backup` по расписанию | каталог из `BACKUPS_DIR` |
| аналитическая база DSP | `deploy.sh backup dsp_analytics` вручную; `scripts/backup.sh` по расписанию | туда же, имя файла `backup_dsp_analytics_*.sql` |
| `uploads` — договоры, креативы, письма о правах | `scripts/backup.sh`, еженедельно | туда же |

`scripts/backup.sh` лежит в корневом `scripts/`, которого **нет в репозитории**: там же
скрипты с реальными реквизитами. На новую машину он передаётся руками.

**Каталог должен быть один.** `BACKUPS_DIR` в `.env` задаёт его и для `deploy.sh` (он
читает `.env` сам — с 11.09.2026; до этого обещание было неверным и каталоги могли
разъехаться молча), и для уборки `retention`, и для монтирования в бэкенд. Если экран состояния смотрит в один каталог, а cron пишет в
другой — «последний бэкап 2 часа назад» будет правдой про чужие файлы.

## Проверить, что бэкап вообще идёт

Экран **Настройки → Состояние системы**, раздел «Бэкапы». Там видно возраст и **имя**
самого свежего файла — имя показывает, чей каталог смотрит бэкенд.

| что видно | что это значит |
|---|---|
| «нет доступа» | каталог не смонтирован в бэкенд; проверка свежести не работает вовсе |
| жёлтый, больше 26 ч | ночной прогон пропущен один раз |
| красный, больше 48 ч | cron мёртв либо дампы не создаются |
| имя вида `before_*` | видны ручные дампы перед миграциями, а не ночные копии — **не тот каталог** |

Второе место — файл `backup_log.txt` в каталоге бэкапов: там строка на каждый прогон,
и удачный, и провальный.

## Ручной бэкап

```bash
cd /root/finance
bash deploy.sh backup
```

Скрипт сам проверяет, что дамп непустой и начинается как дамп; негодный файл **удаляет**
и возвращает ненулевой код. Ротация — последние 14 копий, и она выполняется только после
успешной проверки: иначе пустой файл вытеснял бы годный.

## Восстановление

Делается **на отдельной базе**, не поверх рабочей. Рабочую трогаем только после того,
как убедились, что копия разворачивается.

```bash
# 1. отдельная база рядом
docker exec -i finance_db psql -U finance_user -d postgres -c "CREATE DATABASE finance_restore;"

# 2. развернуть дамп
docker exec -i finance_db psql -U finance_user -d finance_restore < /root/finance/backups/backup_<дата>.sql

# 3. убедиться, что данные на месте — не «прошло без ошибки», а числа
docker exec finance_db psql -U finance_user -d finance_restore -c "
  SELECT (SELECT count(*) FROM operations)    AS операции,
         (SELECT count(*) FROM sales_deals)   AS сделки,
         (SELECT count(*) FROM counterparties) AS контрагенты;"
```

Числа сверить с рабочей базой. Расхождение в пределах суток — норма, на порядок — нет.

Дальше, если восстановление боевое: остановить бэкенд, переименовать базы местами,
поднять бэкенд. Если учебное — удалить `finance_restore`.

**Роль кабинета и расширения.** Дамп основной базы не содержит роль `cabinet` и не
создаёт схему `pub` с нуля — они заводятся миграциями. Аналитическая база требует
расширения TimescaleDB. Поэтому восстановление «на чистый постгрес» — это дамп **плюс**
накат миграций, а не только дамп.

## Учебное восстановление: раз в квартал

Не «когда будет время»: смысл упражнения в том, чтобы найти расхождение до аварии.
Последний раз проводилось **06.09.2026** — прод-дамп развёрнут как отдельная база на
боевых объёмах (3 072 операции, 938 сделок), поверх накатаны 13 миграций дважды, поднят
новый бэкенд, прогнаны восемь ручек и проверка прав не-админом.

**Чего в тот прогон не делали** и стоит добавить в следующий: вход через интерфейс под
живой учёткой и восстановление аналитической базы DSP.

Дату и результат каждого прогона дописывать сюда.

## Чего здесь нет

Копии лежат на той же машине. Отказ диска уносит и базу, и бэкапы — это принятый риск,
он записан в [DEPLOYMENT.md](../../DEPLOYMENT.md). Дампы не зашифрованы.
